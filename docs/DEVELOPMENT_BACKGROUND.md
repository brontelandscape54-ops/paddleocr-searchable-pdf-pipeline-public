# 開発背景と設計判断

[日本語] | [English](DEVELOPMENT_BACKGROUND_en.md)

この文書は、PaddleOCR Searchable PDF Pipeline がどのような実務上の問題から生まれ、どのような比較・失敗・改善を経て現在の形になったかを、公開利用者向けに整理したものです。

これは新しいOCRモデルそのものを提案するプロジェクトではありません。既存のPaddleOCRを、日本語史料・古典籍・宗教団体の刊行物などを実際にOCRアーカイブ化するための、再現可能な処理パイプラインとしてまとめたものです。

## 1. 出発点: 通常本文は処理できても、表を含むページが難しかった

開発のきっかけは、日本語史料をOCRして検索可能なアーカイブを作る実作業でした。

NDL古典OCR-LiteやYomitokuは通常の本文ページでは有用でしたが、実際に文献一覧や一覧表を含むページを処理すると、表内の文字配置や版面の扱いが難しい例がありました。

ここで問題だったのは、単に「OCR文字が1字も読めない」ということではありません。史料のアーカイブ用途では、次の条件を同時に満たしたいからです。

- 表や罫線を含む原ページの見た目を壊さない
- 表の中の文字もできるだけ検索可能にする
- 旧字・異体字・CJK拡張文字をPDF内のUnicodeテキストとして保持する
- 大量ページを手作業ではなく一括処理できる
- OCR後のPDF圧縮でも検索テキストを失わない

この問題から、表に強い候補としてMarker、PaddleOCR等の比較を始めました。

## 2. Markerを表セルの比較基準として利用

Markerは、表のセル境界やTableCell構造を取得する用途で有用でした。

そこでMarkerのTableCell境界を比較用の枠として使い、そのセル内へ各OCRエンジンの文字bboxを割り当てる方法で、表内文字の認識結果を比較しました。

この比較は「MarkerとPaddleOCRのどちらが一般に優れているか」を決めるためのベンチマークではありません。あくまで、実際に処理していた日本語の表資料について、どのOCR結果が実務上使いやすいかを見るための試験です。

PaddleOCRの1ページ試験では次の結果でした。

```text
OCR行数: 214
文字数: 726
平均 confidence: 0.9741
```

Markerのセル境界へPaddleOCRの文字bboxを割り当てた比較では、双方に文字がある182セルのうち158セルが完全一致し、平均文字列類似度は約96.1%でした。

この結果から、この資料ではPaddleOCRの文字認識が十分実用的であると判断し、PaddleOCR単独の本番パイプラインを作る方向へ進みました。

**重要:** これはPaddleOCR単独の表構造復元能力を評価したものではありません。現在の本番パイプラインも、表をExcelのような行・列・セル構造へ完全復元することを主目的にはしていません。

## 3. 「表を再構築する」より「原ページを保持して検索可能にする」

史料用途では、表構造をOCR結果から描き直すと、認識やレイアウト解析の誤りによって原資料の情報が失われることがあります。

そこで現在の検索可能PDFでは、元のページ画像をそのまま表示面として保持し、その上にOCR結果を透明なUnicodeテキストレイヤーとして配置します。

この方式なら、次のような要素は画像として完全に残ります。

- 表組み・罫線
- 挿図・図版
- 印章
- 欄外書き込み
- 変則的な行配置
- 古典籍・史料特有の版面

その上で、OCRできた文字だけを検索・コピー可能にします。

この「原画像保持型」の設計が、現在のrepositoryでいう「図表・複雑な版面に向いている」の意味です。

## 4. PaddleOCRを呼び出すだけでは実用パイプラインにならなかった

PaddleOCRで文字を認識できても、実際のアーカイブ作成にはその前後に多くの処理が必要でした。

現在は次の工程を一括で扱います。

```text
PDF / 画像 / 画像フォルダ
→ 大きすぎるPDFページのOCR-safe前処理
→ ページ画像化
→ PaddleOCR
→ ページ別 compact JSON / TXT
→ TXT / Markdown / JSON / JSONL 統合
→ 検索可能PDF生成
→ ページ結合
→ 抽出テキスト検証
→ 任意のGhostscript圧縮
→ 圧縮後テキスト保持検証
```

途中結果をページ別JSONとして残すため、OCRを再実行せずにPDF生成やフォント処理だけを改善・再検証することもできます。

## 5. 日本語フォントと旧字・異体字の問題

検索可能PDFでは、OCR文字列が正しくても、その文字を埋め込むフォントにUnicodeコードポイントが収録されていなければ、文字が欠落したり抽出できなくなったりします。

初期段階ではM PLUS 1pだけでは足りない文字を別の日本語フォントへフォールバックする実装を作り、文字ごとにTTFのcmapを調べて使用フォントを選ぶ方式へ移行しました。

公開版では、配布条件・再現性・CJK拡張文字のカバレッジを改めて整理し、現在の標準構成を次に統一しています。

```text
MPLUS1p-Medium.ttf
→ Jigmo.ttf
→ Jigmo2.ttf
→ Jigmo3.ttf
```

10ページの実在する日本語史料OCRで旧構成とJigmo構成を比較したところ、両者とも次のcoverageでした。

```text
M PLUS occurrences: 7870
fallback occurrences: 14
fallback unique characters: 9
unsupported characters: 0
```

さらに、Unicode補助面の実在文字 `U+20000` をJigmo2でPDF化し、pypdfで完全一致抽出できることを確認しました。

## 6. Ghostscript圧縮とReportLab ToUnicode CMap

検索可能PDFが生成できても、圧縮後にテキストレイヤーが壊れてはアーカイブ用途として不十分です。

初期にはGhostscript圧縮時にCMap警告が出る問題があり、抽出文字数が保持されているかを毎回検証する仕組みを入れました。

その後、ReportLabが生成するToUnicode CMapについて、次の互換性対策を追加しました。

- `beginbfchar` を最大100 entries単位に分割
- U+FFFFを超えるUnicode宛先をUTF-16BE surrogate pairとして出力

これはsite-packages自体を書き換えず、実行時に適用します。

この修正後、10ページの実資料では通常版検索可能PDFから7766文字を抽出し、Ghostscript 150dpi圧縮後も7766/7766文字、保持率1.000を確認しました。通常版・圧縮版とも従来のCMap警告なしでGhostscript解析に成功しています。

## 7. 大量データと再実行性

PaddleOCRの生結果をそのままJSON保存すると、入力画像配列等を含んで非常に大きくなることがありました。

そのため後段処理に必要な文字、confidence、bbox、polygon等だけを残す `compact-v1` JSONへ移行しました。

初期5ページの比較では、次のように削減できました。

```text
ページJSON合計: 961.3 MiB → 129.3 KiB
ジョブ全体:      2.4 GB → 15 MB
統合処理時間:    47.86秒 → 0.04秒
```

ページ別JSONを再利用できるため、OCRそのものはそのままに、PDFレンダラ・フォント・圧縮処理だけを後から改善できます。

## 8. 文字がないページも保持する

絵画・写真・空白を中心とするページでは、OCR文字が0件になることがあります。

初期実装ではそのようなページを異常とみなして停止していましたが、史料アーカイブではページそのものを落とすべきではありません。

現在はOCR文字が0件でも原ページ画像だけのPDFページとして保持し、ページ数とページ順を維持します。

## 9. 公開版を作る過程で再現性を強化

公開repositoryを作る際には、単にprivateコードから内部情報を削除するだけではなく、第三者がfresh cloneから再構築できることを重視しました。

そのため、次を追加・整理しました。

- `tools/setup.sh` による一括セットアップ
- PaddleOCR環境とhelper環境の分離・固定
- M PLUS / Jigmoフォントの取得とchecksum検証
- ライセンスと第三者ソフトウェアの整理
- PDF/CMap回帰テスト
- `U+20000` を使った補助面実PDF検証
- public tree のprivacy / static smoke test
- private canonical repositoryからallowlistでpublic treeを生成する仕組み

実際に別のcleanなexport treeから `bash tools/setup.sh` を実行し、環境作成・フォント取得・回帰テスト・補助面PDF検証・smoke testまで完走することを確認しています。

## 10. 現在の位置づけと限界

このrepositoryの価値は、PaddleOCRという既存OCRモデルそのものを再発明した点にはありません。

日本語史料の実作業で遭遇した問題を一つずつ処理し、

```text
OCR-safe入力
→ 認識
→ 構造化中間成果物
→ rare CJK font fallback
→ 原画像保持型 searchable PDF
→ CMap互換性
→ 圧縮
→ 圧縮後検証
→ fresh setupによる再現性
```

までを一つの再利用可能なワークフローにまとめたことにあります。

一方で、次の点は明確に限界です。

- 表をCSV / Excelへ完全な論理構造として復元する専用table extractionではない
- PaddleOCRがすべての日本語史料で他のOCRより優れることを主張しない
- Linuxでの完全なend-to-end検証はまだ行っていない
- OCR誤認識そのものを後処理で自動訂正するプロジェクトではない

このpipelineが特に向くのは、**原ページの見た目を資料として保持しながら、本文・表内文字・旧字等をできるだけ全文検索可能にしたい**場合です。

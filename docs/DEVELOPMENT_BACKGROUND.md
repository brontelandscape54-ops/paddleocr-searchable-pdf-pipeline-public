# 開発背景と設計判断

[日本語] | [English](DEVELOPMENT_BACKGROUND_en.md)

この文書は、PaddleOCR Searchable PDF Pipeline がどのような実務上の問題から生まれ、どのような比較・失敗・改善を経て現在の形になったかを、公開利用者向けに整理したものです。

これは新しいOCRモデルそのものを提案するプロジェクトではありません。既存のPaddleOCRを、日本語史料・古典籍・宗教団体の刊行物などを実際にOCRアーカイブ化するための、再現可能な処理パイプラインとしてまとめたものです。

以下に示す処理時間・文字数・セル数・類似度等は、開発時に使用した特定の実資料・機材・設定で得た実測です。**一般性能を示すベンチマークではありません。** 比較の目的は、「この資料を継続的にOCRアーカイブ化するには、どの構成が実務上成立するか」を判断することでした。

## 1. 出発点: 通常本文は処理できても、表を含むページが難しかった

開発のきっかけは、日本語史料をOCRして検索可能なアーカイブを作る実作業でした。

NDL古典OCR-LiteやYomitokuは通常の本文ページでは有用でしたが、実際に文献一覧や一覧表を含むページを処理すると、表内の文字配置や版面の扱いが難しい例がありました。

ここで問題だったのは、単に「OCR文字が1字も読めない」ということではありません。史料のアーカイブ用途では、次の条件を同時に満たしたいからです。

- 表や罫線を含む原ページの見た目を壊さない
- 表の中の文字もできるだけ検索可能にする
- 旧字・異体字・CJK拡張文字をPDF内のUnicodeテキストとして保持する
- 大量ページを手作業ではなく一括処理できる
- OCR後のPDF圧縮でも検索テキストを失わない
- 特定の有料クラウドサービスへ継続的に依存しなくても運用できる

最初にAzure AI Document Intelligence Layoutを実資料で試したところ、表の扱いは非常に良好でした。しかし無料枠が小さく、継続的な大量処理を有料クラウドへ依存する運用は採用しませんでした。

そこで、無料またはローカルで継続利用しやすい候補としてMarker、PaddleOCR、OCRmyPDF/Tesseract等を試し、既に利用していたNDL古典OCR-Lite・Yomitokuとも比較しました。

## 2. 最終成果物はMarkdownや表復元ではなく、原画像保持型searchable PDF

開発初期から、表をMarkdownやCSVへ変換すること自体は最終目的ではありませんでした。

必要だったのは、**原資料の紙面を表示面として保ちながら、認識した文字を検索・コピーできるPDF**です。

そのため基本設計は次の形になりました。

```text
原ページ画像
+
透明Unicode OCR text layer
```

この方式なら、OCRやレイアウト解析が不完全でも、次の情報は原画像としてそのまま残ります。

- 表組み・罫線
- 挿図・図版
- 印章
- 欄外書き込み
- 変則的な行配置
- 古典籍・史料特有の版面

この要求はMarker試験時から一貫しており、現在のPaddleOCR版にもそのまま引き継がれています。

## 3. Marker初期試験: 認識品質は高かったが、処理負荷が大きかった

表に強いローカル候補としてMarkerを実資料へ適用しました。

MarkerでOCRに成功した箇所の品質は非常に良好でした。そのため、Markerを採用しなかった理由は「認識精度が低かったから」ではありません。

一方、当時のApple SiliconノートPC上では処理負荷が大きく、異なる試行で1ページの処理に数分から10分程度を要する例がありました。表認識モデルの一部がMPSを利用できずCPUへfallbackする例もありました。

複数ページPDFをまとめて処理する試験ではMPS backendのメモリ不足も発生し、日常的な大量処理の主力としてそのまま使うのは難しいと判断しました。

重要なのは、ここでMarkerそのものを直ちに捨てたわけではないことです。品質が高かったため、重い部分を切り分けながら利用する方法をしばらく検討しました。

## 4. Markerの `blocks.json` からsearchable PDFを自作

MarkerはMarkdown / JSON / HTMLなどの構造化出力には向いていましたが、開発時点の標準的な使い方では、必要としていた「原画像 + 透明テキスト」のsearchable PDFを直接得る形ではありませんでした。

そこでdebug出力の `blocks.json` を調べ、Text / Line / Span系ブロックから文字列とbboxを取得し、ReportLabで透明テキストを原画像上へ配置する後処理を作りました。

処理は概ね次の形です。

```text
Marker
→ blocks.json
→ text + bbox を抽出
→ 左上原点座標をPDF左下原点へ変換
→ bboxに合わせて透明テキストを配置
→ searchable PDF
```

1ページ試験では213 spanを配置し、通常のsearchable PDFと位置確認用PDFを生成できました。見た目と検索レイヤーの位置関係も良好でした。

つまり、Markerを最終採用しなかった理由は、**searchable PDFを作れなかったからでもありません**。Marker OCR結果を用いた原画像保持型searchable PDFは実際に成立していました。

## 5. OCRmyPDF / Tesseractへ一度切り替えたが、対象資料では精度が不足

Markerの複数ページ処理が重かったため、より単純で軽量なsearchable PDF生成手段としてOCRmyPDF / Tesseractも試しました。

しかし、当時処理していた日本語表資料ではMarkerと比べて認識精度が落ちると判断しました。そのため「軽い既成searchable-PDFツールへ置き換える」のではなく、**Markerの高い認識・構造解析能力のうち必要な部分だけを残し、重い部分を別OCRへ置き換えられないか**という方向へ戻りました。

この寄り道は、後の「レイアウト・表構造」と「文字認識」を分離して考える設計につながっています。

## 6. ページ分割・低解像度化・CPU実行でも、文字認識がボトルネックになった

複数ページでのメモリ不足を避けるため、PDFを1ページずつ画像化し、画像長辺を抑え、CPU実行・スレッド数制限などを使う安全化も試しました。

OCR専用converterも試しましたが、当時の出力ではsearchable PDF生成に必要な `blocks.json` が得られないケースがあり、通常converterへ戻す必要がありました。

代表的な表ページでは、Marker内部のSurya文字認識に対して次のログが得られました。

```text
Recognizing Text: 224/224
所要時間: 約12分20秒
```

この試験により、Markerのすべての処理が等しく重いのではなく、**文字認識部分が主要なボトルネック**であることが見えてきました。

### 開発時の速度実測をどう解釈したか

開発中には、条件の異なる複数試行から次のような時間記録が残りました。

| 試行 | 開発時の実測例 | 当時の判断に使った意味 |
| --- | ---: | --- |
| Marker通常処理の一例 | 約605秒 | 1ページでも実運用上重い例がある |
| Marker JSON系試行の一例 | 約458秒 | JSON出力にしても軽量化とはいえない |
| Marker / Surya文字認識 | 224領域で約12分20秒 | 文字認識が主要ボトルネックと切り分ける材料 |
| Marker OCR無効・TableCell検出 | 168セルで約4秒 | 表構造検出自体は高速 |
| PaddleOCR smallの一例 | 約3.81秒 | 軽量な文字認識候補として実用性が高い |

**注意:** これは同一入力・同一解像度・同一処理範囲で揃えた速度ベンチマークではありません。異なる段階・設定の開発ログを並べ、「どの処理がボトルネックだったか」「どの構成なら実用化できそうか」を説明するための履歴です。

そこで次に、Markerを「表構造だけ取る部品」として使い、文字認識を別OCRへ分離する方向へ進みました。

## 7. Markerを表構造だけに使うと、非常に軽くなった

MarkerのTableConverterとOCR無効化設定を使い、文字認識を走らせず、表領域・行列・TableCellのbboxだけを取得する試験を行いました。

実資料の1ページでは、**168セルの座標を約4秒で取得**できました。

ここで設計したハイブリッド構成は次の形です。

```text
Marker
  → 表構造・TableCell bbox

別OCR
  → ページ全体を1回だけ認識

座標照合
  → OCR bboxをMarkerセルへ割り当て

原画像 + 透明テキスト
  → searchable PDF
```

168セルを個別に168回OCRするのではなく、ページ全体を一度だけ認識し、そのbboxをセルへ割り当てる方が効率的でした。複数行セルにも対応しやすくなります。

この段階で、Markerの表構造認識は有用である一方、Surya文字認識だけを別エンジンへ置き換えれば実用化できる可能性が見えました。

## 8. NDL / Yomitoku / Marker / PaddleOCRを同一ページで比較

別OCR候補を選ぶため、同じ表ページについて複数方式の出力を比較しました。

比較対象は次の5方式です。

```text
Marker
NDL古典OCR-Lite
Yomitoku-lite
Yomitoku-full
PaddleOCR small
```

まず最終テキストを同じ規則で正規化し、非空白文字数・日本語文字数・漢字・かな・英字・数字・行数を比較しました。

```text
tool              非空白   日本語   漢字   かな   英字   数字   行数
-----------------------------------------------------------------
Marker               754      435    416     19     48    188     44
NDL                  836      407    396     11     31    200    213
Yomitoku-lite        823      423    412     11     29    200     38
Yomitoku-full        813      432    420     12     20    202     38
Paddle-small         717      425    413     12     19    202    214
```

これは文字数が多いほど良いという評価ではありません。各OCRが行分割・読順・句読点・英数字を異なる単位で出すため、まず「出力特性がどの程度違うか」を見るための表です。

## 9. 全文文字列類似度も計算したが、精度指標とは扱わなかった

同じ正規化文字列同士について、参考値として文字列類似度も計算しました。

```text
Marker vs NDL:           0.176
Marker vs Yomitoku-lite: 0.832
Marker vs Yomitoku-full: 0.851
Marker vs Paddle-small:  0.862
NDL vs Yomitoku-lite:    0.197
NDL vs Yomitoku-full:    0.204
NDL vs Paddle-small:     0.179
Yomitoku-lite vs full:   0.951
Yomitoku-lite vs Paddle: 0.842
Yomitoku-full vs Paddle: 0.859
```

PaddleOCR smallは、この比較ではMarkerの最終文字列に最も近い値でした。

ただし、この類似度は**OCR精度そのものではありません**。表を行ごとに読むかセルごとに読むか、改行をどう入れるか、どの順序で連結するかによって大きく変わるためです。

この限界が明確だったため、次により空間的なセル単位比較へ進みました。

## 10. 原画像付き168セル比較表を作成

Markerが検出した168セルを空間的な比較基準とし、各セルの原画像と各OCRの認識文字を横並びに表示するHTML/CSV比較表を作りました。

概ね次の項目を各セルごとに並べました。

```text
原画像
多数一致
Marker
Yomitoku-lite
Yomitoku-full
NDL
Paddle-small
```

色分けも行い、文字のある全方式が一致するセル、空欄があるセル、文字列が異なるセルを視覚的に区別しました。PaddleOCRについては、そのセルへ割り当てた認識領域の平均confidenceも併記しました。

この比較では、多数決一致を正解とはみなしませんでした。必ず左側の原画像と照合し、OCR間で同じ誤りをしている可能性も残しました。

この段階で、単なる総文字数・全文類似度よりも、実際の原画像に対して各OCRがセル単位で何を読んだかを確認できるようになりました。

## 11. 評価方法自体も段階的に改善した

この開発では、OCRエンジンを一つの数値で順位づけするのではなく、比較方法そのものを段階的に改善しました。

```text
総文字数・文字種比較
↓
全文文字列類似度
↓
読み順・改行差の影響が大きいと判断
↓
Marker 168セル + 原画像を並べたHTML/CSV比較
↓
Marker TableCellへ各OCR bboxを空間割り当て
↓
同一セル内での文字列比較
```

特に重要だったのは、**OCR同士の多数決をground truthにしなかったこと**です。複数OCRが同じ誤読をする可能性があるため、セル比較では原画像を横に置き、人間が直接照合できるようにしました。

この方針により、単純な全文類似度を「精度」と誤解することを避け、実際の史料上の各セルで何が起きているかを確認できました。

## 12. 231個のMarker TableCellを共通基準にすると、PaddleOCRの相対差が明瞭だった

評価をさらに精密化するため、後のMarker `blocks.json` で確認された
21行×11列 = 231個の明示的TableCellを比較フレームとして使いました。

これは前節までの168セル比較とは別段階です。
168セルはOCRを無効にしたlayout-only経路で得た比較フレームであり、
231セルはOCRを含む別のMarker出力で確認された明示的TableCellです。

231セル版では、Markerは各 `TableCell.text_lines`、
Yomitoku-lite / fullは21行×11列のMarkdown表、
NDL / PaddleOCRは文字bboxをMarkerセルへ空間的に割り当てて比較しました。

PaddleOCRの1ページ試験では次の値を得ていました。

- OCR領域: 214
- 文字数: 726
- 平均confidence: 0.9741

この231セル比較でMarkerとの平均文字列類似度を比べると、

| OCR | Markerとの平均文字列類似度 |
| --- | ---: |
| Yomitoku-lite | 87.1% |
| Yomitoku-full | 87.9% |
| NDL | 77.6% |
| Paddle-small | 96.1% |

でした。

セル単位の完全一致率は、

| OCRペア | 完全一致 / 双方文字あり | 完全一致率 |
| --- | ---: | ---: |
| Marker × Yomitoku-lite | 121 / 187 | 64.7% |
| Marker × Yomitoku-full | 125 / 187 | 66.8% |
| Marker × NDL | 114 / 184 | 62.0% |
| Marker × Paddle-small | 158 / 182 | 86.8% |

でした。

つまり当時重要だったのは、Paddle-smallの平均類似度が96.1%だったという
絶対値だけではありません。同じMarkerセル基準の中で、
PaddleOCRがYomitoku-fullより8.2ポイント、Yomitoku-liteより9.0ポイント、
NDLより18.5ポイント高い平均類似度を示し、
完全一致率でもそれぞれ20.0、22.1、24.8ポイント高かったことが、
PaddleOCRを単なる軽量候補以上のものとして見る強い材料になりました。

ただし、Markerはground truthではありません。
Marker自身が誤るセルもあり、多数決も正解とは限らないため、
この比較は一般的なOCR精度ランキングではなく、
特定の日本語表資料・当時の設定における相対比較です。

また、NDL / PaddleOCRのbboxをMarkerセルへ割り当てる過程では、
隣接文字や重複文字が同じセルへ入る可能性もありました。
したがって、セル比較上の差分をすべて純粋な文字認識誤りとはみなしません。

それでも、この比較は
**PaddleOCR単独でも実用的な文字認識とbboxを得られる可能性が高い**
と判断する大きな材料になりました。
そして最終成果物が論理的な表復元ではなく原画像保持型searchable PDFだったため、
Marker TableCellへの再割当工程そのものを本番から省けることも、
後の単独化につながりました。

## 13. なぜMarker + PaddleOCRハイブリッドを最終採用しなかったのか

ここまでの比較では、Marker + PaddleOCRハイブリッドも技術的には十分可能でした。

Markerには次の長所がありました。

- OCRに成功した箇所の文字品質が高い
- TableCell構造を取得できる
- OCRを切れば表セル検出は高速
- `blocks.json` からsearchable PDFを作れる

一方で、ハイブリッド構成にすると、

```text
Marker表構造
+
PaddleOCR文字認識
+
座標系変換
+
セル割り当て
+
PDFレンダリング
```

という複数段階を常に保守する必要があります。

しかも最終目的は、表をExcelやHTMLの論理セル構造へ完全復元することではなく、**原ページ画像を保持しつつ表内文字も検索できるPDFを作ること**でした。

PaddleOCR単独で十分な文字列とbboxが得られるなら、TableCell構造を本番パイプラインへ必ず持ち込む必要はありません。

そのため本番構成は、より単純な

```text
ページ画像
→ PaddleOCR
→ text + bbox
→ 原画像上へ透明Unicodeテキスト
→ searchable PDF
```

へ収束しました。

したがって、Markerを採用しなかった理由は、**精度が悪かったからではなく、最終要件に対してPaddleOCR単独の方が十分で、処理・依存関係・保守の構成を簡素化できたから**です。

## 14. PaddleOCRを呼び出すだけでは実用パイプラインにならなかった

PaddleOCRで文字を認識できても、実際のアーカイブ作成にはその前後に多くの処理が必要でした。

現在は次の工程を一括で扱います。

```text
PDF / 画像 / 画像フォルダ
→ 大きすぎるPDFページのOCR-safe前処理
→ ページ画像化
→ PaddleOCR
→ ページ別 compact JSON / TXT
→ TXT / Markdown / JSON / JSONL 統合
→ 検索可能PDF生成
→ ページ結合
→ 抽出テキスト検証
→ 任意のGhostscript圧縮
→ 圧縮後テキスト保持検証
```

途中結果をページ別JSONとして残すため、OCRを再実行せずにPDF生成やフォント処理だけを改善・再検証することもできます。

## 15. 日本語フォントと旧字・異体字の問題

検索可能PDFでは、OCR文字列が正しくても、その文字を埋め込むフォントにUnicodeコードポイントが収録されていなければ、文字が欠落したり抽出できなくなったりします。

初期段階ではM PLUS 1pだけでは足りない文字を別の日本語フォントへフォールバックする実装を作り、文字ごとにTTFのcmapを調べて使用フォントを選ぶ方式へ移行しました。

公開版では、配布条件・再現性・CJK拡張文字のカバレッジを改めて整理し、現在の標準構成を次に統一しています。

```text
MPLUS1p-Medium.ttf
→ Jigmo.ttf
→ Jigmo2.ttf
→ Jigmo3.ttf
```

10ページの実在する日本語史料OCRで旧構成とJigmo構成を比較したところ、両者とも次のcoverageでした。

```text
M PLUS occurrences: 7870
fallback occurrences: 14
fallback unique characters: 9
unsupported characters: 0
```

さらに、Unicode補助面の実在文字 `U+20000` をJigmo2でPDF化し、pypdfで完全一致抽出できることを確認しました。

## 16. Ghostscript圧縮とReportLab ToUnicode CMap

検索可能PDFが生成できても、圧縮後にテキストレイヤーが壊れてはアーカイブ用途として不十分です。

初期にはGhostscript圧縮時にCMap警告が出る問題があり、抽出文字数が保持されているかを毎回検証する仕組みを入れました。

その後、ReportLabが生成するToUnicode CMapについて、次の互換性対策を追加しました。

- `beginbfchar` を最大100 entries単位に分割
- U+FFFFを超えるUnicode宛先をUTF-16BE surrogate pairとして出力

これはsite-packages自体を書き換えず、実行時に適用します。

この修正後、10ページの実資料では通常版検索可能PDFから7766文字を抽出し、Ghostscript 150dpi圧縮後も7766/7766文字、保持率1.000を確認しました。通常版・圧縮版とも従来のCMap警告なしでGhostscript解析に成功しています。

## 17. 大量データと再実行性

PaddleOCRの生結果をそのままJSON保存すると、入力画像配列等を含んで非常に大きくなることがありました。

そのため後段処理に必要な文字、confidence、bbox、polygon等だけを残す `compact-v1` JSONへ移行しました。

初期5ページの比較では、次のように削減できました。

```text
ページJSON合計: 961.3 MiB → 129.3 KiB
ジョブ全体:      2.4 GB → 15 MB
統合処理時間:    47.86秒 → 0.04秒
```

ページ別JSONを再利用できるため、OCRそのものはそのままに、PDFレンダラ・フォント・圧縮処理だけを後から改善できます。

## 18. 文字がないページも保持する

絵画・写真・空白を中心とするページでは、OCR文字が0件になることがあります。

初期実装ではそのようなページを異常とみなして停止していましたが、史料アーカイブではページそのものを落とすべきではありません。

現在はOCR文字が0件でも原ページ画像だけのPDFページとして保持し、ページ数とページ順を維持します。

## 19. 公開版を作る過程で再現性を強化

公開repositoryを作る際には、単にprivateコードから内部情報を削除するだけではなく、第三者がfresh cloneから再構築できることを重視しました。

そのため、次を追加・整理しました。

- `tools/setup.sh` による一括セットアップ
- PaddleOCR環境とhelper環境の分離・固定
- M PLUS / Jigmoフォントの取得とchecksum検証
- ライセンスと第三者ソフトウェアの整理
- PDF/CMap回帰テスト
- `U+20000` を使った補助面実PDF検証
- public tree のprivacy / static smoke test
- private canonical repositoryからallowlistでpublic treeを生成する仕組み

実際に別のcleanなexport treeから `bash tools/setup.sh` を実行し、環境作成・フォント取得・回帰テスト・補助面PDF検証・smoke testまで完走することを確認しています。

## 20. 現在の位置づけと限界

このrepositoryの価値は、PaddleOCRという既存OCRモデルそのものを再発明した点にはありません。

日本語史料の実作業で遭遇した問題を一つずつ処理し、

```text
OCR-safe入力
→ 認識
→ 構造化中間成果物
→ rare CJK font fallback
→ 原画像保持型 searchable PDF
→ CMap互換性
→ 圧縮
→ 圧縮後検証
→ fresh setupによる再現性
```

までを一つの再利用可能なワークフローにまとめたことにあります。

一方で、次の点は明確に限界です。

- 表をCSV / Excelへ完全な論理構造として復元する専用table extractionではない
- PaddleOCRがすべての日本語史料で他のOCRより優れることを主張しない
- 上記の比較値は特定資料・特定設定の開発時実測であり、一般ベンチマークではない
- Linuxでの完全なend-to-end検証はまだ行っていない
- OCR誤認識そのものを後処理で自動訂正するプロジェクトではない

このpipelineが特に向くのは、**原ページの見た目を資料として保持しながら、本文・表内文字・旧字等をできるだけ全文検索可能にしたい**場合です。
